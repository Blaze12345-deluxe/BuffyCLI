buffy/

      interpreter.rs      interpret() - walk AST, dispatch to handlers.

      variable.rs         resolve() - ${VAR} expansion with regex.

      verify.rs           verify_package() - SHA-256 per-file verification.

      discover.rs         discover() - system scan for tool detection.

      aliases.rs          Aliases and conflict preferences.

2.  CRATE DEPENDENCIES
================================================================================

Crate dependencies are defined in Cargo.toml. The key decisions:

clap and clap_complete:
  CLI argument parsing and shell completion generation. clap is the industry
  standard for Rust CLI tools. clap_complete integrates directly with clap's
  Command API for shell completion output.

serde and serde_json:
  JSON serialization for all configuration files (config.json, installed.json,
  repositories.json, aliases.json) and package manifests (package.json).

ureq (NOT reqwest):
  Synchronous HTTP client. Deliberately chosen over reqwest to avoid needing
  an async runtime. Used for all GitHub API calls (fetching indexes,
  downloading packages, checking for updates).

sha2:
  SHA-256 hashing for package verification. Direct hash computation without
  higher-level crypto abstractions.

thiserror and anyhow:
  thiserror for deriving Error implementations on BuffyError and BslError.
  anyhow for top-level error handling in main().

dirs:
  Cross-platform home directory resolution. Used to find ~/.buffy/.

colored:
  Terminal color output. Simple API for green checkmarks, red X marks,
  yellow warnings, and cyan info labels.

chrono:
  Timestamps for log filenames, date-based versioning, install dates.

indicatif:
  Progress bars and spinners for package installation operations.

regex-lite (NOT full regex):
  Lighter regex engine for ${VAR} expansion. The only regex pattern is
  \$\{\w+\}, which doesn't need the full regex crate.

tempfile:
  Temporary directories for package download and extraction.

tracing and tracing-subscriber:
  Structured logging framework. Writes daily log files to ~/.buffy/logs/.


================================================================================
3.  MODULE ARCHITECTURE
================================================================================

The codebase is organized into 8 subsystems plus the error module:

BASE LAYERS (depend on nothing except std/crates):
  config          - Configuration file I/O, path resolution.
  logger          - Terminal output formatting.
  bsl             - BSL language interpreter (lexer, parser, executor).
  error           - Error types used by everyone.

UPPER LAYERS (depend on base layers):
  resolver        - Command resolution (depends on config).
  cli             - CLI parsing and dispatch (depends on everything).
  package         - Package management (depends on config, repository, bsl).
  repository      - GitHub integration (depends on config).
  diagnostic      - System checks (depends on config, package, bsl).

This layering prevents circular dependencies and allows testing base layers
in isolation.

================================================================================
5.  DATA FLOWS
================================================================================

5.1  General Execution Flow

  User types "buffy pip-env create project"
    -> main() calls lib::run()
      -> ensure_directories() creates ~/.buffy/ if needed
      -> ensure_bundled_packages() installs pip-env on first run
      -> init_logging() opens daily log file
      -> CliArgs::parse() parses arguments
      -> cli::dispatch::execute() routes to handler
        -> No flags match, so treat as BSL command
          -> resolver::tree::resolve(["pip-env", "create"])
            -> alias resolution on first arg
            -> walk ~/.buffy/commands/pip-env/create.bsl
          -> bsl::interpreter::run(script, ["project"])
            -> lexer: tokenize source text
            -> parser: build AST from tokens
            -> interpreter: walk AST, execute each instruction
              -> WRITE "text"  =>  println!(variable::resolve(text))
              -> RUN "cmd"     =>  executor::execute(cmd, output_mode)
              -> WAIT 5        =>  thread::sleep(5s)
              -> EXIT          =>  break

5.2  Package Install Flow

  User types "buffy --install pip-env"
    -> dispatch calls package::install::install(["pip-env"])
      -> install_from_repositories(["pip-env"])
        -> read ~/.buffy/repositories.json
        -> for each repository URL:
          -> repository::github::fetch_index_cached(owner, repo)
            -> check ~/.buffy/cache/indexes/ for cached index
            -> if missing or corrupt, fetch from GitHub and cache
          -> index.find_package("pip-env")
          -> install_from_github(repo_url, ["pip-env"])
            -> download package.json, SHA.txt, .bsl files to temp dir
            -> verify_package() => SHA-256 per-file comparison
            -> detect_conflict() => check installed.json for name conflicts
            -> resolve_dependencies() => system + BSL deps
            -> copy files to ~/.buffy/commands/pip-env/
            -> register in installed.json

5.3  BSL Script Processing Pipeline

  Source Text (.bsl file)
    -> LEXER: tokenize() strips comments, produces Vec<(usize, Token)>
    -> PARSER: parse() builds BslScript { metadata, statements }
    -> VARIABLE RESOLVER: resolve() expands ${HOME}, ${USER}, ${1}, etc.
    -> INTERPRETER: interpret() walks statements sequentially
    -> EXECUTOR: execute() spawns shell for RUN commands, captures I/O

================================================================================
7.  ERROR HANDLING STRATEGY
================================================================================

The project uses two error types:

BuffyError (src/error.rs):
  Top-level errors for CLI dispatch and package management. Each variant
  includes a user-facing tip in its display message.  Common variants:
    CommandNotFound        - suggests --list or --repo search
    AmbiguousCommand       - multiple packages provide the same .bsl filename
                             (dispatch shows a numbered selection prompt)
    PackageNotFound        - suggests --repo search or --repo add <url>
                             (or just --repo <url> as shorthand)
    ConfigError            - suggests --repair or --reset
    CircularDependency     - suggests checking dependency declarations
    BslRuntime             - suggests OUTPUT = true to see command output
    PackageVerificationFailed - suggests reinstalling or updating

BslError (src/bsl/error.rs):
  BSL-specific errors for the interpreter. Variants:
    Syntax                 - parse errors with line numbers
    UnknownInstruction     - rejected with available instructions list
    CommandFailed          - shows command, exit code, stderr
    Runtime                - general runtime error
    Io                     - IO error wrapper

Error propagation:
  Library functions return Result<T, BuffyError> or Result<T, BslError>.
  Main uses anyhow::Result for top-level handling.
  BSL runtime errors stop execution immediately.


================================================================================
8.  TESTING STRATEGY
================================================================================

Unit tests are inline in each module (#[cfg(test)] mod tests).
Integration tests are in tests/integration/.
Test fixtures are in tests/fixtures/.

Test isolation:
  - tempfile::TempDir for each test's home directory.
  - TEST_HOME_LOCK mutex serializes tests that modify HOME.
  - No test writes to the real ~/.buffy/.

Coverage:
  BSL: 20+ tests (lexer, parser, pipeline, variables, executor).
  Resolver: 8 tests (all resolution paths + flat lookup).
  Package: 15+ tests (manifest, verify, deps, discover).
  Repository: 10+ tests (source parsing, index, cached fetch).
  Config: 8 tests (buffy_home, aliases, settings).
  Diagnostic: 6 tests (lint, validate).

# Project: Buffy CLI Automation Framework

I want to build a cross-platform command-line application called **Buffy**. Buffy is a lightweight automation framework that allows users to create and share terminal commands without writing Python or Bash. Instead, commands are written in a custom scripting language called **BSL (Buffy Script Language)**.

The goal is to make creating CLI automations as simple as writing a text file.

---

# Project Goals

Buffy should be:

* Lightweight
* Fast
* Modular
* Extensible
* Safe
* Easy to learn
* Easy to package and distribute
* Open source

The executable itself should be very small. Nearly all functionality should come from installable `.bsl` modules.

---

# Core Idea

When the user runs a command such as:

```bash
buffy pip-env
```

Buffy searches its installed command library, finds the matching `.bsl` script, interprets it, executes every instruction in order, and then returns control to the user's shell.

Users should never need to know Python or Bash to create commands.

---

# Buffy Script Language (BSL)

BSL is a simple interpreted scripting language.

Example:

```text
VERSION = "1.0.0"
AUTHOR = "Buffy Community"
DESCRIPTION = "Creates a Python virtual environment."

OUTPUT = false

WRITE "Creating virtual environment..."

RUN "python3 -m venv .venv"

WRITE "Upgrading pip..."

RUN ".venv/bin/python -m pip install --upgrade pip"

WRITE "Done."

EXIT
```

The interpreter executes instructions from top to bottom.

Comments begin with:

```text
//
```

Example:

```text
// This is ignored
```

# Command Resolution

Commands are resolved from the directory structure.

Example:

```
~/.buffy/

commands/

    pip-env/
        module.bsl

    restart/
        docker.bsl

    docker/
        compose/
            up.bsl
```

Examples:

```
buffy pip-env
```

loads

```
commands/pip-env/module.bsl
```

```
buffy restart docker
```

loads

```
commands/restart/docker.bsl
```

```
buffy docker compose up
```

loads

```
commands/docker/compose/up.bsl
```

The runtime should walk the folder tree using each command-line argument until it finds the appropriate `.bsl` file.

# Buffy Home Directory

Everything Buffy stores should live inside a hidden directory.

```
~/.buffy/
```

Example layout:

```
~/.buffy/

commands/

cache/
logs/

```

This keeps all Buffy data isolated from the rest of the system.

# Package System

Buffy includes a built-in package manager.

Packages consist primarily of `.bsl` files plus metadata.

The runtime installs packages into:

```
~/.buffy/commands/
```

---

# Installing Packages

Install from configured repositories:

```bash
buffy install pip-env
```

Install from a local file:

```bash
buffy install ./pip-env.bsl
```

Install from a specific GitHub repository:

```bash
buffy install github.com/ExampleUser/custom-buffy-plugins pip-env
```

or

```bash
buffy install https://github.com/ExampleUser/custom-buffy-plugins pip-env
```

Install multiple packages from one repository:

```bash
buffy install github.com/ExampleUser/custom-buffy-plugins pip-env apt-update docker-tools
```

Install every package from a repository:

```bash
buffy install github.com/ExampleUser/custom-buffy-plugins @
```

The `@` symbol means "install every package in this repository."

---

# Repository System

Buffy should support:

* One official repository by default.
* Multiple configured repositories.
* Installing directly from any public GitHub repository.

Configured repositories are stored in:

```
~/.buffy/repositories.json
```

Example:

```json
[
    "https://github.com/Blaze12345-deluxe/Buffy-Plugins",
    "https://github.com/Example/community-packages",
    "https://github.com/MyName/private-packages"
]
```

When installing a package without specifying a repository, Buffy should:

1. Search every configured repository.
2. Compare package versions.
3. Install the newest compatible version.

If multiple repositories contain the same version, the repository appearing first in `repositories.json` wins.

Repositories should contain an `index.json` listing every package and its metadata. Buffy should download this index rather than scanning the repository, improving performance and reducing GitHub API requests.

# Runtime Responsibilities

The Buffy executable should only:

* Parse command-line arguments.
* Locate `.bsl` files.
* Parse the BSL language.
* Validate syntax.
* Expand variables.
* Execute instructions.
* Manage repositories.
* Install and update packages.
* Display errors.
* Return control to the shell.

The runtime should **not** contain hard-coded automation commands.

Automation should come from installable `.bsl` packages.

# Interpreter Requirements

The interpreter should:

* Parse line-by-line.
* Ignore comments.
* Validate metadata before execution.
* Support quoted strings.
* Produce useful syntax errors with line numbers.
* Validate every instruction before running it.
* Hide command output when `OUTPUT = false`.
* Always display stderr if a command fails.
* Stop execution on fatal errors unless future error-handling instructions are added.

# Architecture

The project should be split into well-defined components.

Suggested architecture:

* CLI argument parser
* Command resolver
* BSL lexer
* BSL parser
* Interpreter
* Variable resolver

Each component should be independent and easily testable.

# Preferred Implementation

Use a language suitable for building a fast CLI application, such as Rust or Go. The implementation should be clean, modular, well documented, and designed for long-term maintainability. Avoid tightly coupling the interpreter, package manager, and repository manager so that each subsystem can evolve independently.

Please produce a complete architecture, directory structure, implementation plan, and step-by-step development roadmap before writing code. Then implement the project in incremental, well-tested stages rather than attempting everything at once.
